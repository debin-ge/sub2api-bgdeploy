## 1. 背景与问题陈述

### 1.1 现状

Sub2API 当前的部署形态为单机 Docker Compose:一个 Go 应用容器 + PostgreSQL + Redis,由宿主机上的 Nginx 做 TLS 终止与反向代理。仓库内虽有 `deploy/Caddyfile`,但生产环境实际使用 Nginx。

发布动作等价于 `docker compose pull && docker compose up -d`,期间应用容器被销毁重建。

### 1.2 问题

**P1:发布必然中断在途请求,且中断是有损的。**

Sub2API 是 AI API 网关,主要流量为流式响应(SSE)。`GATEWAY_IMAGE_STREAM_DATA_INTERVAL_TIMEOUT` 默认 900 秒,单条图像生成流可持续 15 分钟。而应用的优雅关闭窗口只有 5 秒:

```go
// backend/cmd/server/main.go:182
ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
defer cancel()

if err := app.Server.Shutdown(ctx); err != nil {
    log.Fatalf("Server forced to shutdown: %v", err)   // :186
}
```

叠加 compose 未配置 `stop_grace_period`(Docker 默认 10 秒后 SIGKILL),容器最多存活 10 秒。**每次发布都会把所有在途流拦腰截断**,客户端表现为流中途断开、无结束事件,Agent 类客户端(Claude Code / Codex CLI)会话直接失败。

`log.Fatalf` 还带来次生问题:关闭超时以非 0 码退出,在 `restart: unless-stopped` 下产生无意义的重启记录,干扰故障判断。

**P2:多站点多环境的配置文件数量线性膨胀。**

每新增一个站点或环境,需要人工编写一份 nginx server block 和一份 docker-compose.yml,并手工分配宿主机端口、避免容器名冲突。当前 compose 存在三处硬编码容器名:

```yaml
# deploy/docker-compose.yml:20 及另两处
container_name: sub2api
container_name: sub2api-postgres
container_name: sub2api-redis
```

多站点部署会直接命名冲突。配置散落且互相复制粘贴,极易产生漂移(某个站点漏配 `proxy_buffering off`,SSE 就被 nginx 缓冲住)。

**P3:发布失败没有安全网。**

当前流程中,新版本容器启动失败或健康异常时,旧容器已被销毁,只能靠重新拉起旧镜像恢复,期间服务完全不可用。没有「先验证再切流量」的机制,也没有秒级回滚路径。

### 1.3 与备选方案的差异

| 方案 | 位置 | 局限 |
|---|---|---|
| Docker Swarm(单机) | 编排器 | 解决的是多节点调度,本场景痛点是单机连接排空;Swarm 处于维护模式,有状态服务挂载别扭 |
| K3s / Nomad | 编排器 | 单机 VPS 上纯属运维负债 |
| Traefik / nginx-proxy + docker-gen | 反代自动发现 | 免写 conf,但 SSE 所需的细粒度 proxy 参数需靠 per-container 模板覆盖,调试链路变长 |
| Kamal / kamal-proxy | 专用部署工具 | 契合度高,但要引入新的目录与配置约定,与现有 compose 体系重叠;且需替换现有 Nginx |
| **本需求(Nginx + Docker 双容器)** | **复用现有 Nginx** | 不引入新组件,SSE 参数完全可控,`nginx -s reload` 天然不中断旧 worker 上的在途连接 |

选择本方案的决定性理由:**Nginx reload 时旧 worker 会保留在途连接直至自然结束**,这与 Sub2API 的长 SSE 流特征高度契合,是其他反代方案需要额外机制才能达到的效果。

## 2. 目标与非目标

### 2.1 目标

| # | 目标 | 度量 |
|---|---|---|
| G1 | 发布不中断在途请求 | 发布期间持续流式压测,SSE 流中断数 = 0 |
| G2 | 发布不产生服务不可用窗口 | 发布期间 HTTP 5xx 与 502/504 计数 = 0 |
| G3 | 新版本异常时线上零影响 | 健康门禁失败的发布,流量从未切换,线上错误率无变化 |
| G4 | 提供秒级回滚能力 | 排空窗口内回滚命令端到端 < 10 秒 |
| G5 | 新增站点的人工成本恒定 | 新增站点仅需改一条清单记录 + 填一个 env 文件 + 申请证书,不写 nginx conf 与 compose yml |
| G6 | 配置不漂移 | 所有站点的 compose 与 nginx server block 由同一组模板渲染,产物可随时重新生成并比对 |

### 2.2 非目标(明确不做)

- **不做多节点高可用**。本方案解决「发布不中断」,不解决「宿主机宕机」。后者需多节点 + 外部 LB,不在本期范围;
- **不做数据库层的蓝绿**。PostgreSQL / Redis 常驻,不参与 slot 轮换;
- **不做自动化的 schema 回滚**。回滚只回滚应用代码,已应用的迁移不撤销(见 §8.1);
- **不改动单站点用户的现有部署方式**。`deploy/docker-compose.yml` 与 `docker-compose.local.yml` 的使用方式保持兼容;
- **不引入编排器**(Swarm / K8s / Nomad);
- **不接管证书管理**。certbot 续期流程不变,方案只引用证书路径;
- **不做金丝雀 / 按比例灰度**。本期是二元切换(全量 blue 或全量 green),按比例分流见 §12。

## 3. 用户与场景

### 3.1 角色

| 角色 | 描述 | 与本需求的关系 |
|---|---|---|
| 运维/发布负责人 | 在服务器上执行发布、回滚、排障 | 主要使用者,直接操作 CLI |
| 后端开发 | 提交代码与数据库迁移 | 受 §8.1 迁移契约约束 |
| 平台终端用户 | 通过 API 调用网关的 CLI Agent 用户 | 无感知受益方——发布时会话不再中断 |

### 3.2 用户故事

- 作为发布负责人,我希望发布新版本时,**正在跑的 15 分钟图像生成流不会被打断**,这样用户不会在发布窗口内收到莫名其妙的失败;
- 作为发布负责人,我希望新版本起不来时**流量根本不切过去**,而不是切过去之后再手忙脚乱地回退;
- 作为发布负责人,我希望发现问题后能**一条命令在 10 秒内退回上一个版本**;
- 作为发布负责人,我希望新增一个站点时**不用再手写 nginx conf**,避免又漏配某个 SSE 参数;
- 作为后端开发,我希望有一份**明确的迁移编写规则**,知道什么样的迁移不能用蓝绿发布。

### 3.3 典型场景

**场景 A:常规发布**
CI 构建并推送 `v1.4.3` 镜像 → 发布负责人执行 `s2a-deploy api-prod v1.4.3` → 脚本在闲置 slot 拉起新容器(此时执行 DB 迁移)→ 健康检查通过 → 改写 nginx upstream 单行并 reload → 旧 slot 进入 960 秒排空期 → 排空结束自动回收。全程线上无中断。

**场景 B:发布失败**
新版本因配置校验失败无法启动 → 健康门禁在 300 秒后超时 → 脚本打印容器日志并自动回收新 slot → **流量从未切换,线上零影响** → 发布负责人根据日志修复后重试。

**场景 C:发布后发现异常**
流量已切至 green,5 分钟后监控告警 → 执行 `s2a-rollback api-prod` → blue 容器仍在排空期内运行 → 改回 upstream + reload,秒级恢复。

**场景 D:新增站点**
在 `sites.yaml` 增加一条记录 → 填写该站点的 env 文件(密钥)→ certbot 申请证书 → `s2a-render` 渲染产物 → `s2a-init` 初始化 → `s2a-deploy` 首次部署。

## 4. 产品方案概述

### 4.1 一句话描述

用 Nginx upstream 的单行改写 + reload 完成流量切换,同一站点维持 blue/green 两个应用容器轮换发布;所有站点的 compose 与 nginx 配置由一份 `sites.yaml` 清单加四份模板渲染产生。

### 4.2 架构

```
                    公网 :443
                        │
                 ┌──────▼───────┐
                 │  Nginx (宿主) │  TLS 终止 / 多域名 / SSE 透传
                 └──────┬───────┘
        ┌───────────────┼───────────────┐
        │ upstream      │ upstream      │ upstream
        │ api-prod      │ api-staging   │ site2-prod
        ▼               ▼               ▼
  127.0.0.1:18080  127.0.0.1:18090  127.0.0.1:18100
        │
   ┌────┴─────────────────────────────┐
   │  stack: api-prod                 │
   │  ┌────────────┐  ┌────────────┐  │  ← 蓝绿只在这层
   │  │ app-blue   │  │ app-green  │  │
   │  │ :18080     │  │ :18081     │  │
   │  └─────┬──────┘  └─────┬──────┘  │
   │        └───────┬───────┘         │
   │        ┌───────▼────────┐        │  ← 常驻,不参与蓝绿
   │        │ postgres │redis│        │
   │        └────────────────┘        │
   │        共享 bind mount: ./data    │
   └──────────────────────────────────┘
```

### 4.3 设计原则(工程承诺)

| # | 原则 | 含义 |
|---|---|---|
| D1 | 单一真相源 | 站点配置只在 `sites.yaml`;当前生效 slot 只看 nginx upstream 文件 |
| D2 | 先验证后切换 | 流量切换发生在健康门禁通过之后,不可逆操作前置校验 |
| D3 | 失败不影响线上 | 任何发布前置步骤失败,均自动回收新 slot 且不触碰 upstream |
| D4 | 排空优先于回收 | 旧容器停止接收新请求后保留足够时间让在途流自然结束 |
| D5 | 对单站点用户零影响 | 现有 compose 文件与文档中的使用方式保持可用 |
| D6 | 产物可重新生成 | 渲染脚本幂等,任何时候重跑不影响运行中的容器 |

## 5. 功能需求

优先级:P0 = 本期必须;P1 = 本期应有,可延后至阶段 4;P2 = 二期。

### FR-1 应用优雅关闭窗口可配置(P0)

**描述**:应用收到 SIGTERM 后,应等待在途请求自然结束再退出,等待时长可通过环境变量配置。

| # | 需求点 |
|---|---|
| FR-1.1 | 新增环境变量 `SERVER_SHUTDOWN_TIMEOUT_SECONDS`,取值为正整数秒;未设置或非法时使用默认值 |
| FR-1.2 | 默认值由当前的 5 秒调整为 30 秒。5 秒对流式网关在任何部署形态下都过短 |
| FR-1.3 | 关闭开始时输出日志,包含实际生效的超时值 |
| FR-1.4 | 关闭超时**不得**以非 0 码退出。超时仅表示仍有连接未结束,应记录 warning 后正常退出 |
| FR-1.5 | `deploy/.env.example` 补充该变量的说明,并注明与 `GATEWAY_IMAGE_STREAM_DATA_INTERVAL_TIMEOUT` 的关系:`shutdown ≥ stream + 余量` |

**影响文件**:`backend/cmd/server/main.go`(182–187 行,import 需新增 `strconv`)、`deploy/.env.example`

**验收**:设置 `SERVER_SHUTDOWN_TIMEOUT_SECONDS=120` 并发起一条持续中的 SSE 流,执行 `docker stop`,该流应完整收到结束事件后容器才退出;容器退出码为 0。

### FR-2 蓝绿发布编排(P0)

**描述**:提供 `s2a-deploy <slug> [tag]` 命令,完成从拉起新容器到切换流量的完整流程。

| # | 需求点 |
|---|---|
| FR-2.1 | 从 nginx upstream 文件读取当前生效端口,推导当前 slot 与目标 slot |
| FR-2.2 | 部署前确保该 stack 的数据层(postgres/redis)处于 healthy 状态 |
| FR-2.3 | 在目标 slot 拉起指定 tag 的镜像;未指定 tag 时使用清单中记录的 tag |
| FR-2.4 | 蓝绿两个 slot 必须共享同一份 `/app/data` 挂载(其中含 `config.yaml` 与 `.installed`),否则新 slot 会被识别为全新安装 |
| FR-2.5 | 数据层与应用层拆分为独立的 compose project,发布过程中数据库容器不重启 |
| FR-2.6 | 应用容器的 `stop_grace_period` 必须 ≥ `SERVER_SHUTDOWN_TIMEOUT_SECONDS`,两者绑定同一变量 |
| FR-2.7 | 应用端口仅绑定 `127.0.0.1`,不对公网暴露 |
| FR-2.8 | 部署命令在流量切换完成后即返回,排空与回收异步执行 |

**验收**:执行发布,`docker ps` 可见两个 app 容器并存,postgres 容器的 `Created` 时间未变化;应用端口 `ss -lntp` 显示仅监听 127.0.0.1。

### FR-3 健康门禁与失败自动回收(P0)

**描述**:新 slot 必须通过健康检查才允许切换流量;未通过则自动回收且不触碰线上。

| # | 需求点 |
|---|---|
| FR-3.1 | 轮询新 slot 的 `/health`,间隔可配(默认 3 秒),总超时可配(默认 300 秒) |
| FR-3.2 | 超时阈值必须覆盖数据库迁移时间。迁移在容器启动时执行,超时上限为 10 分钟 |
| FR-3.3 | 门禁失败时:打印新 slot 最近 200 行日志 → 销毁新 slot → 以非 0 码退出 → **不修改 nginx 配置** |
| FR-3.4 | 改写 upstream 后必须执行 `nginx -t`;校验失败则还原备份文件并回收新 slot,不执行 reload |
| FR-3.5 | `/health` 响应中应包含版本号,供脚本校验实际启动的镜像与预期 tag 一致(见 FR-8.1) |

**验收**:人为构造一个必然启动失败的镜像(如错误的 DB 密码),执行发布,应在超时后自动回收,`curl` 线上域名全程返回 200。

### FR-4 秒级回滚(P0)

**描述**:提供 `s2a-rollback <slug>`,在排空窗口内将流量切回上一个 slot。

| # | 需求点 |
|---|---|
| FR-4.1 | 优先走快速路径:上一 slot 容器仍在运行且健康检查通过时,仅改写 upstream + reload |
| FR-4.2 | 快速路径不可用(容器已回收)时,降级为以上一个 tag 重新执行完整发布流程,并明确提示耗时不同 |
| FR-4.3 | 回滚时必须取消该 stack 待执行的排空定时器,避免回滚后目标容器被定时任务销毁 |
| FR-4.4 | 回滚前必须校验目标 slot 健康,不健康则拒绝执行并给出明确提示 |
| FR-4.5 | 回滚**不撤销数据库迁移**,该行为需在文档与命令输出中明示 |

**验收**:发布后立即回滚,端到端耗时 < 10 秒,期间流式压测无中断。

### FR-5 多站点清单化配置(P0)

**描述**:所有站点的配置集中在一份清单文件,compose 与 nginx 产物由模板渲染。

| # | 需求点 |
|---|---|
| FR-5.1 | 提供 `sites.yaml`,含 `defaults` 段与 `stacks` 列表;每条记录含 slug、域名、端口基址、镜像 tag、TLS 证书路径、排空与门禁时长 |
| FR-5.2 | 密钥类配置(数据库密码、`JWT_SECRET`、`TOTP_ENCRYPTION_KEY`、OAuth secret 等)**不进入清单**,保留在各站点独立的 env 文件,权限 600 |
| FR-5.3 | 提供 `s2a-render`,读取清单渲染出:每站点的两份 compose、每站点的 nginx server block;渲染完成后执行 `nginx -t`,通过才 reload |
| FR-5.4 | 渲染必须幂等:重复执行不影响运行中的容器,不覆盖已存在的 upstream 文件 |
| FR-5.5 | 渲染前校验:端口区间无重叠、域名无重复、TLS 证书文件存在。任一校验失败则中止并报错 |
| FR-5.6 | 端口分配规则:每 stack 占用 10 个端口的区间,blue 用 `port_base`,green 用 `port_base+1`,其余预留 |
| FR-5.7 | compose 模板中**不得**出现 `container_name`,容器命名由 compose project name 派生 |

**验收**:新增第三个站点仅需修改清单一条记录 + 填一个 env 文件 + 申请证书,`s2a-render` 后三个站点的域名均可正常访问且互不干扰。

### FR-6 Nginx 流式透传配置(P0)

**描述**:所有站点共用一份 proxy 参数片段,确保 SSE 语义正确。

| # | 需求点 |
|---|---|
| FR-6.1 | 提供公共 snippet,含 `proxy_buffering off`、`proxy_cache off`、`proxy_request_buffering off`、`gzip off`——缺任一项都会破坏 SSE |
| FR-6.2 | `proxy_read_timeout` / `proxy_send_timeout` 必须 ≥ 应用侧的流间隔超时(默认 900 秒) |
| FR-6.3 | `proxy_http_version 1.1` + `proxy_set_header Connection ""`,保持与 upstream 的 keepalive |
| FR-6.4 | 转发头只从真实 TCP 对端生成,不透传客户端提交的 `X-Forwarded-For` 等值 |
| FR-6.5 | 显式设置 `worker_shutdown_timeout`(建议 1200 秒)。nginx 默认不设置意味着旧 worker 永不强制退出,频繁 reload 会堆积进程 |
| FR-6.6 | `/metrics` 路径在 nginx 层返回 404,作为应用侧 bearer 校验之外的第二道防线 |

**验收**:新建站点的 SSE 首字节延迟与既有站点一致(无缓冲导致的批量吐出);`curl -H 'X-Forwarded-For: 1.2.3.4'` 时应用侧记录的 IP 为真实客户端 IP。

### FR-7 部署状态查询(P1)

**描述**:提供 `s2a-status [slug]`,展示所有 stack 的实际状态。

| # | 需求点 |
|---|---|
| FR-7.1 | 输出每个 stack:域名、当前生效 slot 与端口、两个 slot 的容器状态与镜像 tag、各 slot 的 `/health` 探测结果 |
| FR-7.2 | 展示待执行的排空定时器及其剩余时间 |
| FR-7.3 | 当「状态记录文件」与「nginx 实际配置」不一致时,以 nginx 配置为准并高亮告警 |

**验收**:手工制造状态文件与 nginx 配置不一致的情形,命令应明确指出差异。

### FR-8 部署可观测性(P1)

| # | 需求点 |
|---|---|
| FR-8.1 | `/health` 响应体增加 `version` 与 `slot` 字段,供发布脚本校验实际运行的镜像 |
| FR-8.2 | 容器日志配置轮转上限(建议 `max-size 50m` / `max-file 5`),避免多站点多容器撑满磁盘 |
| FR-8.3 | 发布成功/失败结果可推送至告警渠道(阶段 3 随 CI 集成落地) |

### FR-9 就绪探针(P2,二期)

新增 `/readyz`,执行一次数据库与 Redis 探活。用于强化健康门禁语义与监控告警。该路径不对公网暴露。

## 6. 交互需求(CLI)

本需求无 Web UI,交互载体为服务器上的命令行工具。

## 8. 约束与前置条件

### 8.1 数据库迁移契约(硬约束,不可协商)

**背景**:`backend/internal/repository/ent.go:72` 在创建 Ent client 时调用 `applyMigrationsFS`,即**每次容器启动都会执行迁移**。该过程受 PostgreSQL Advisory Lock 保护,并通过 `schema_migrations` 表 + SHA256 校验和防止重复与篡改,因此并发启动不会冲突。

**推论**:蓝绿发布意味着新 slot 一启动就把 schema 升级到版本 N,而此时旧 slot(版本 N-1 的代码)仍在服务同一个数据库。并存窗口最短数十秒,最长等于排空时长。

**因此,每个版本的迁移必须与上一个应用版本兼容(expand-contract)**:

| 操作 | 允许 | 正确做法 |
|---|---|---|
| `ADD COLUMN`(可空或有默认值) | ✅ | 直接添加 |
| `ADD COLUMN NOT NULL` 无默认值 | ❌ | 拆两步:先可空 → 回填 → 下个版本加约束 |
| `DROP COLUMN` / `DROP TABLE` | ❌ | 版本 K 停止读写 → 版本 K+1 才删除 |
| `RENAME COLUMN` | ❌ | 加新列 → 双写 → 回填 → 停用旧列 → 下版本删除 |
| `ALTER COLUMN ... TYPE` | ❌ | 加新列 → 双写 → 切换读 → 删除旧列 |
| `CREATE INDEX` | ⚠️ | 必须 `CONCURRENTLY`,且不能包在事务中(迁移 runner 默认用事务包裹,需单独处理) |

**回滚的额外约束**:回滚只将流量切回旧 slot,**不撤销已应用的迁移**。因此旧代码必须能在新 schema 上正常运行——这正是 expand-contract 所保证的。**破坏该规则的版本不能使用蓝绿发布,必须安排停机窗口。**

**配套要求**:CI 增加门禁,迁移文件 diff 中出现 `DROP COLUMN|DROP TABLE|RENAME|ALTER COLUMN .* TYPE` 时,要求 PR 显式打 `breaking-migration` 标签方可合并。

### 8.2 并存窗口的进程内状态约束

**进程内并发闸**:`backend/internal/handler/openai_gateway_handler.go:2096` 的 `GATEWAY_IMAGE_CONCURRENCY_MAX_CONCURRENT_REQUESTS` 是进程内信号量。并存窗口内,打到上游的实际并发为配置值的 2 倍。上游有配额或风控时需评估影响。

缓解:短期按 `ceil(N/2)` 配置;长期迁移至基于 Redis 的分布式限流(Redis 已是必备组件)。

**后台定时任务**:并存窗口内,基于 ticker 或 cron 触发的后台 goroutine 会同时运行两份(radar 聚合、清理任务等)。

**前置动作**:实施前必须专项排查 `backend/internal/` 下所有后台循环任务,确认其幂等性。不幂等的任务需通过 Redis 锁或 PG Advisory Lock 保护。**该排查是阶段 0 的交付物之一,不通过则不进入阶段 1。**

**数据目录写竞争**:`/app/data` 被两个 slot 同时挂载。`config.yaml` 在首次安装后不再重写(`.installed` 存在时 `NeedsSetup()` 返回 false),但需确认无其他运行时写入该目录的逻辑会互相覆盖。

### 8.3 环境前置条件

- 宿主机已安装 nginx 且具备 reload 权限;
- 宿主机已安装 docker 与 docker compose v2;
- 各站点域名的 TLS 证书已由 certbot 签发,且续期 hook 中包含 `nginx -s reload`;
- 端口区间 18080 起可用。

## 11. 边界情况与异常处理

| 情形 | 预期行为 |
|---|---|
| 新 slot 健康检查超时 | 打印日志 → 销毁新 slot → 非 0 退出;**nginx 配置未被触碰,线上无影响** |
| `nginx -t` 校验失败 | 还原 upstream 备份 → 回收新 slot → 非 0 退出;不执行 reload |
| 迁移执行失败 | 新 slot 启动失败,退化为「健康检查超时」路径;旧版本继续服务 |
| 迁移长时间未完成 | 健康门禁超时阈值需 ≥ 迁移超时(10 分钟)。若门禁先超时,新 slot 被回收但迁移可能已部分完成——迁移本身是单文件事务的,不会留下半个迁移 |
| Advisory Lock 被僵尸容器持有 | 排障入口:`SELECT * FROM pg_locks WHERE locktype='advisory'` |
| 排空期内再次发布 | 目标 slot 仍有在途流,回收操作会等待其排空。脚本应给出明确提示而非静默阻塞 |
| 回滚时旧 slot 已被回收 | 降级为完整重新发布,命令输出必须明示耗时差异 |
| 两个 slot 状态与记录不一致 | 一律以 nginx upstream 文件为准(D1);状态文件仅作辅助记录 |
| 端口被非本方案的进程占用 | `s2a-render` 校验阶段报错;若绕过校验,`docker compose up` 会失败并被健康门禁路径捕获 |
| 证书过期或路径错误 | `s2a-render` 校验证书文件存在性;内容有效性由 `nginx -t` 兜底 |
| 磁盘被容器日志撑满 | FR-8.2 的日志轮转上限,每容器上限 250MB |
| 数据层容器意外停止 | 发布前的数据层健康检查会拦截,发布中止 |

## 12. 二期规划(Roadmap,非本期承诺)

1. **排空由定时改为探测**。当前 960 秒定时排空是保守值。应用暴露 `sub2api_http_requests_in_flight` gauge 后,回收脚本可轮询该指标,归零即回收,`DRAIN_SECONDS` 降级为上限;
2. **按比例灰度**。nginx upstream 支持 weight,可实现 90/10 分流后再全量,配合错误率自动判停;
3. **分布式限流**。将进程内并发闸迁至 Redis,消除 §8.2 的并发翻倍问题;
4. **共享数据库实例**。站点数超过约 5 个时,改为单 PG 实例 + 每站点独立 database/role。需先将迁移的 Advisory Lock key 由常量改为按 database 区分;
5. **多节点高可用**。本方案的 nginx 层可平移至多节点 + 外部 LB 架构;
6. **清单纳入版本管理**。`sites.yaml` 迁入独立私有仓库,变更走 review。

## 15. 术语表

| 术语 | 含义 |
|---|---|
| Stack | 一个站点 + 环境的组合(如 `api-prod`),含独立的应用、数据库、Redis 与域名 |
| Slot | 一个 stack 内的应用容器位,取值 blue 或 green,两者轮换承载流量 |
| 排空(Drain) | 旧 slot 停止接收新请求后,保留运行以让在途请求自然结束的过程 |
| 健康门禁 | 流量切换前对新 slot 的健康检查,不通过则不切换 |
| Expand-Contract | 数据库迁移策略:先做兼容性扩展,待旧版本下线后再做收缩清理 |
| 快速回滚 | 旧 slot 容器仍在运行时,仅改写 upstream 完成的回滚,秒级 |
| 降级回滚 | 旧 slot 已被回收时,以旧 tag 重新发布完成的回滚,分钟级 |
| 清单(sites.yaml) | 所有站点配置的单一真相源,不含密钥 |
